# Установка и запуск «Пар'ИМБА'нк»

Это инструкция для разработчика или оператора. Для участника сайта предназначено [отдельное руководство](USER_GUIDE_RU.md), для команды — [руководство администратора](ADMIN_GUIDE_RU.md).

## 1. Требования

| Компонент | Требование |
| --- | --- |
| Node.js | Версия 22.13 или новее |
| npm | Установленный вместе с поддерживаемым Node.js |
| Python | Python 3 для SQL-тестов; не нужен серверу при обычной работе |
| ОС для локальной разработки | Windows, macOS или Linux |
| Размещение | Cloudflare Worker с D1 и R2; в Sites ресурсы привязывает платформа |
| Авторизация | Проверенная личность Sites; вне Sites требуется отдельная защищённая интеграция |

Копируйте исходники с `package-lock.json`, папками `scripts/`, `drizzle/`, `public/`, конфигурацией и всеми компонентами. Не переносите чужие локальные базы и каталоги инструментов. В чистом клоне без `.sites-runtime/execution-profile.json` автоматически выбирается профиль `portable`. В управляемом окружении Sites профиль назначает платформа; вручную менять его для обычной публикации не нужно.

## 2. Установка зависимостей и локальная конфигурация

Откройте терминал в корне проекта:

```sh
node --version
npm run install:ci
node -e "const fs=require('node:fs');fs.copyFileSync('config/env.example','.dev.vars',fs.constants.COPYFILE_EXCL)"
```

Последняя команда создаёт локальную конфигурацию. Если `.dev.vars` уже существует, она остановится с `EEXIST`, сохранив прежние значения. Используйте существующую конфигурацию или сначала сделайте её резервную копию. Не запускайте несколько установок зависимостей одновременно. `install:ci` использует зафиксированный lockfile и включает инструменты сборки, необходимые проекту.

В `config/env.example` указан только вымышленный локальный аккаунт `seedy@sites.test`. Файл `.dev.vars` игнорируется Git. Для серверных окружений значения задаются секретами платформы, а не включаются в исходники.

| Имя | Назначение |
| --- | --- |
| `APP_OWNER_EMAIL` | Email подтверждённого аккаунта владельца. В локальном переносимом режиме — `seedy@sites.test` |
| `APP_ADMIN_EMAILS` | Список email для однократного первоначального назначения администраторов. Разделители: запятая, точка с запятой или новая строка |
| `DB` | Привязка D1, не строка подключения и не переменная из браузера |
| `BUCKET` | Привязка R2 для изображений призов |
| `TELEGRAM_BOT_USERNAME` | Необязательное имя подключаемого бота без `@` |
| `TELEGRAM_BRIDGE_SECRET` | Необязательный серверный секрет Telegram bridge; при подключении должен совпасть с процессом бота |

Привязки D1/R2 объявлены в `.openai/hosting.json`; локально их создаёт эмулятор. Не вставляйте ключи Cloudflare, пароль или идентификатор пользователя вместо этих привязок.

## 3. Сборка и создание локальной базы

```sh
npm run build
npm run db:migrate:local
```

Сборка создаёт `dist/server/wrangler.json`. Помощник миграций читает из него локальный идентификатор D1, создаёт временную конфигурацию в игнорируемом `.sites-runtime/local-migrations/` и применяет SQL из `drizzle/` через механизм миграций Wrangler. Исходные SQL-файлы не меняются. Выполненные файлы учитываются в `d1_migrations`, поэтому обычный повтор команды безопасен и применяет только новые миграции.

Разработка, собранный локальный Worker и помощник по умолчанию используют `.wrangler/state`. Указывайте корень состояния, не `.wrangler/state/v3`: версию каталогов добавляет Wrangler.

Для отдельной проверки установки, не затрагивающей рабочую локальную базу:

```sh
npm run db:migrate:local -- --persist-to .wrangler/migration-check
npm run db:migrate:local -- --persist-to .wrangler/migration-check
```

Эта отдельная база не подключается к `npm run dev` автоматически. Второй запуск проверяет отсутствие повторного применения уже учтённых миграций. Команда всегда использует `--local` и не меняет производственную D1.

### Старая локальная база без журнала миграций

В предыдущих версиях SQL мог применяться через `d1 execute --file` без журнала Wrangler. Если помощник обнаружит таблицы приложения без записей миграций, он остановится. Не запускайте все старые SQL повторно и не отмечайте их выполненными вслепую: реальная схема может отличаться.

Остановите локальный сервер и сохраните полную копию `.wrangler/state`. Если данные нужны, разработчик должен сравнить схему и миграции, определить фактически выполненные файлы и подготовить согласованный переход. Если локальные данные не нужны, сохраните старый каталог под другим именем и создайте новую локальную базу командой `db:migrate:local`. Помощник не удаляет и не переименовывает данные сам. Это правило относится только к локальной разработке; производственную базу обслуживают отдельно с резервной копией.

## 4. Запуск и первый вход

```sh
npm run dev
```

Откройте URL из терминала, обычно `http://localhost:5173`. Для другого порта:

```sh
npm run dev -- --port 5174
```

В переносимом режиме локальный вход запускается адресом `/signin-with-chatgpt?return_to=/admin` на этом же сервере. Он создаёт тестовую личность `local_seedy` с email `seedy@sites.test`. При значении `APP_OWNER_EMAIL` из примера эта личность становится владельцем локального проекта. Выход доступен через `/signout-with-chatgpt?return_to=/`.

**Dev-сервер предназначен только для разработки на своём компьютере.** Кроме локальной имитации входа, сервис имеет резервную dev-личность владельца при отсутствии пользовательской личности. Поэтому выход в dev-режиме не является проверкой анонимного доступа. Не выставляйте dev-сервер в публичную сеть; проверки прав проводите серверными тестами и отдельными аккаунтами в защищённом окружении. В производственной сборке резервная dev-личность и имитация входа отключены.

Новая база не создаёт готовые розыгрыши, вымышленных участников или билеты. Откройте `/admin` → «Розыгрыши» → «Создать розыгрыш», заполните приз и условия. Изображение необязательно; без него отображается нейтральное оформление. Подробнее — в [руководстве администратора](ADMIN_GUIDE_RU.md).

## 5. Проверки

```sh
npm run check
npm run build
```

`check` запускает TypeScript и все файлы тестов `tests/test-*.mjs` и `tests/test_*.py`. Python должен быть доступен как `python3` или `python`. Тесты проверяют права, операции с балансом, целостность билетов и возвратов, переписку, историю, приглашения и изображения. Они используют изолированные тестовые базы, а не рабочую D1.

GitHub Actions повторяет проверки и сборку, затем дважды применяет локальные миграции к новой временной базе. Рабочий сайт, облачные ресурсы и секреты не используются. Успешный CI не заменяет проверку интерфейса и реальной интеграции входа.

Перед выпуском вручную проверьте:

1. Вход владельца, администратора, модератора и обычного участника; запрет доступа постороннему к `/admin`. Проверьте сохранение настроек администратором, назначение/снятие ролей и блокировку другого администратора; собственные роль/статус и аккаунт настоящего владельца должны оставаться защищёнными.
2. Создание розыгрыша с собственным призом и изображением, выбор города и начало в нужное время.
3. Запрос монет, решение по нему, выдачу билетов, завершение и уведомления.
4. Отмену незавершённого события с однократным возвратом монет.
5. Переписку двух аккаунтов и отсутствие внутренних заметок в ответе участнику.
6. Работу на узком экране, клавиатурную навигацию, ошибки и повтор загрузки.
7. Резервное копирование и восстановление данных в отдельном окружении.

Для локального запуска уже собранного Worker:

```sh
npm start
```

Используйте адрес из вывода. Этот режим не публикует сайт и не имитирует вход. Без доверенной интеграции личности защищённые страницы и API будут недоступны; это ожидаемое отличие от `dev`.

## 6. Публикация через Sites

1. Сохраните привязку существующего проекта в `.openai/hosting.json`. Для независимой копии зарегистрируйте новый проект через Sites и используйте его конфигурацию; не отправляйте копию под идентификатором чужого проекта.
2. Убедитесь, что для проекта подключены `DB` и `BUCKET` и применена вся последовательность миграций.
3. Установите `APP_OWNER_EMAIL` в серверной конфигурации по проверенному аккаунту владельца. При необходимости заполните `APP_ADMIN_EMAILS` явным списком приглашённых сотрудников.
4. Настройте аудиторию сайта в платформе. Приглашение на закрытый сайт и роль в приложении — разные разрешения.
5. Выполните стандартные проверки, сборку и публикацию средствами Sites. После публикации проверьте вход, данные, создание и открытие изображения на опубликованном адресе.

Платформа обслуживает `/signin-with-chatgpt`, `/signout-with-chatgpt` и `/callback` и передаёт серверу подтверждённую личность. Эти маршруты не нужно реализовывать повторно внутри приложения. У приложения нет собственного пароля администратора. Удаление email из первоначального списка не отзывает уже выданную роль: другой администратор или владелец меняет её в панели.

## 7. Самостоятельное производственное размещение

Репозиторий содержит Worker, но команда публикации Worker сама по себе не создаёт безопасную авторизацию. До публичного размещения вне Sites оператор должен реализовать и проверить доверенный шлюз входа либо заменить адаптер личности проверенной серверной сессией. Входящие от клиента сведения о личности должны удаляться или игнорироваться; обход шлюза прямым обращением к origin должен быть исключён. Только после проверки личности сервер может сопоставлять email с `APP_OWNER_EMAIL` и `APP_ADMIN_EMAILS`.

Также нужны собственные Cloudflare Worker, D1, R2, привязки `DB`/`BUCKET`, производственные секреты, домен с HTTPS, миграции, обработка входа и выхода, мониторинг и резервное копирование. Текущие пути входа рассчитаны на Sites; без соответствующего защищённого обработчика они не станут работать автоматически. `npm start` остаётся локальным средством проверки, а не инструкцией безопасного публичного запуска.

Для настройки платформенных ресурсов используйте [документацию Cloudflare Workers](https://developers.cloudflare.com/workers/), [D1](https://developers.cloudflare.com/d1/) и [R2](https://developers.cloudflare.com/r2/). Способ самостоятельной авторизации и публикации зависит от выбранного шлюза и не скрыт за фиктивной «готовой» командой в этом репозитории.

## Telegram: бесплатный Worker или отдельный процесс

Основной вариант — отдельный webhook на Cloudflare Workers Free. Папка `bot/` публикуется независимо от сайта: Git root directory `bot`, build `npm test && npm run build`, deploy `npm run deploy`. Настройки, лимиты бесплатного тарифа и пошаговая активация — в [CLOUDFLARE_RU.md](../bot/CLOUDFLARE_RU.md). Worker выключен, пока `BOT_ENABLED` не задан явно как `true`; рабочие токены вводятся только в runtime secrets.

Основной сайт не становится публичным webhook-приёмником: транспорт обращается к его закрытому `/api/telegram/bridge` с сервисным доступом Sites и отдельным секретом. Аудитория сайта сохраняется. Для Workers не нужны offset-файл или платный постоянный процесс.

Альтернатива — long polling на собственном Linux-сервере; подготовленный Render Blueprint является платным и не был применён. Нужны настоящий токен BotFather, согласованное имя и секреты; до их настройки и проверки привязки/участия бот не считается запущенным. Команды пользователя и оба варианта транспорта — в [TELEGRAM_RU.md](TELEGRAM_RU.md).

## 8. Обновления, данные и секреты

Перед обновлением сохраните резервные копии базы и нужных объектов R2. Не редактируйте уже применённые миграции — добавляйте новые. После изменения привязок пересоберите проект. Локальные миграции и миграции опубликованной базы выполняются раздельно.

Все прежние события с `is_demo=1` архивируются и становятся недоступными для нового набора. Пять известных стартовых событий без реальных покупок скрываются полностью; история настоящих участий сохраняется для команды и владельцев билетов. История, билеты и баланс не очищаются автоматически; администрация проверяет такие записи отдельно. Не удаляйте таблицы, чтобы получить «чистый» каталог.

Не добавляйте в Git `.dev.vars`, `.env*`, `.wrangler/`, `.sites-runtime/`, `node_modules/`, собранный `dist/`, приватные ключи, выгрузки с персональными данными или резервные копии. В репозитории должны оставаться пример конфигурации, исходники и миграции. Владелец и администратор имеют равные возможности в приложении, но назначение роли не передаёт владение Sites, репозиторием GitHub и хостингом и не выдаёт доступ к их настройкам.

## 9. Частые проблемы

| Проблема | Что проверить |
| --- | --- |
| Нет `dist/server/wrangler.json` | Выполните `npm run build` перед локальными миграциями |
| `no such table` | Примените миграции к той же локальной базе `.wrangler/state`; для опубликованного сайта проверьте производственные миграции |
| База имеет таблицы без истории миграций | Следуйте разделу о старой локальной базе; не повторяйте все SQL вручную |
| Нельзя открыть `/admin` | Проверьте подтверждённый аккаунт, роль и `APP_OWNER_EMAIL`; обычное приглашение не всегда назначает роль |
| Изображения не загружаются | Проверьте `BUCKET`, права сотрудника и формат JPEG/PNG/WebP; предел — 5 МиБ, 40 мегапикселей и 20 000 пикселей по стороне |
| Нельзя получить билет | Проверьте статус аккаунта, баланс, начало события, свободные билеты и включённое участие |
| Старая карточка не возобновляется | Архивные стартовые события не допускают нового участия; создайте новый розыгрыш |
| Тесты не находят Python | Установите Python 3 и проверьте команду `python3 --version` или `python --version` |
| Порт занят | Остановите предыдущий dev-сервер или передайте другой `--port` |
| После повторного входа не вернулись права сотрудника | Первоначальный grant применяется один раз; последующие роли меняет другой администратор или владелец в панели |

Готовность к рабочему запуску определяется не только сборкой: должны быть проверены действующая авторизация, резервное восстановление, реальные условия и наличие призов, процесс их передачи и работа поддержки. Платежи, доставка призов и внешние рассылки приложением не подключаются.
