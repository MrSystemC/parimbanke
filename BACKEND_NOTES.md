# Сервер и эксплуатация «Пар'ИМБА'нк»

Приложение работает как Cloudflare Worker с Vinext. D1 хранит состояние проекта, R2 — изображения призов. Новая база пуста: автоматического наполнения событиями, участниками или билетами нет. Монеты бесплатные, платёжный провайдер не подключён. Пользовательские сценарии описаны в [руководстве участника](docs/USER_GUIDE_RU.md), действия команды — в [руководстве администратора](docs/ADMIN_GUIDE_RU.md), запуск — в [INSTALL_RU.md](docs/INSTALL_RU.md).

## Личность и права

В размещении Sites проверенную личность ChatGPT передаёт платформа; `app/chatgpt-auth.ts` читает её в серверном контексте. Стабильный пользовательский ID служит ключом записей. Email применяется для сопоставления с серверной конфигурацией, а не принимается из формы роли. Вне Sites требуется доверенный шлюз авторизации либо адаптер проверенной сессии, исключающий подмену клиентских сведений и прямой обход шлюза. Сам Worker не проверяет OAuth-подпись платформенных заголовков.

`APP_OWNER_EMAIL` задаётся как серверный секрет по подтверждённому аккаунту владельца. Только совпадающий подтверждённый email может инициализировать или восстановить привязку владельца. Устаревшая привязка первого посетителя из старой версии отзывается при явной конфигурации владельца. Вход владельца восстанавливает его активное состояние. Согласование привязки выполняется транзакционно.

`APP_ADMIN_EMAILS` — явный список для однократного первоначального назначения администратора. Совпадение проверяется по подтверждённому email. Активный подходящий аккаунт получает роль и запись аудита; маркер в `app_meta` предотвращает повторное назначение после ручного изменения роли. Заблокированные аккаунты не разблокируются этим списком. Удаление адреса из списка не отзывает существующую роль: другой администратор или владелец меняет её в панели. Приглашение на закрытый сайт и административная роль приложения — разные разрешения.

Владелец и администратор имеют одинаковые прикладные полномочия: управляют настройками, балансом, запросами монет, розыгрышами, поддержкой, журналом и другими пользователями. Оба могут назначать другому пользователю роли `user`, `moderator` и `admin`, снимать административные права, блокировать и разблокировать других администраторов. Роль `owner` через панель не назначается. Роль и статус фактического владельца, а также собственные роль и статус изменять нельзя. Модератор сохраняет ограниченный доступ к событиям, поддержке, пользователям и журналу без финансовых действий, назначения ролей и сохранения настроек. Заблокированный сотрудник теряет административный доступ; обычный заблокированный пользователь сохраняет чтение данных и обращения в поддержку в пределах настроек приёма.

Равенство полномочий не меняет привязку владельца: `isOwner` остаётся признаком только фактического владельца, определённого серверной конфигурацией. Роль администратора приложения не выдаёт владение Sites, репозиторием GitHub или инфраструктурой хостинга и не позволяет менять их настройки.

Переносимый dev-режим имеет локальную имитацию входа и резервную dev-личность. Они не включены в производственную сборку. Не используйте публично доступный dev-сервер или его выход из аккаунта для проверки реальной анонимной авторизации.

## Данные и миграции

D1 хранит пользователей, события, билеты, покупки с ключами повторного запроса, запросы монет, операции баланса, уведомления, переписки, внутренние заметки, корректировки, настройки, журнал действий и метаданные изображений.

| Миграция | Назначение |
| --- | --- |
| `0000_remarkable_gorilla_man.sql` | Исходная схема |
| `0001_event_invariants.sql` | Транзакционные правила участия и монет |
| `0002_flaky_sauron.sql` | Администрация, поддержка и дополнительные ограничения |
| `0003_operational_guards.sql` | Проверка глобальных переключателей при записи |
| `0004_wonderful_deathstrike.sql` | Призы, метаданные изображений, запрет нового участия в прежних архивных событиях и обновлённые уведомления |
| `0005_prize_identity_lock.sql` | Транзакционная фиксация типа, наименования и изображения приза после первого билета |
| `0006_fearless_tyrannus.sql` | Постоянные категории, запросы и подтверждённые привязки Telegram, намерения получения билетов |

Уже применённые миграции неизменяемы. Новые изменения добавляются отдельным файлом. Старые одноразовые контактные сообщения переносятся в переписки идемпотентно на уровне сервиса, отдельно от схемы.

`npm run db:migrate:local` применяет недостающие миграции через Wrangler только к локальной D1 и ведёт `d1_migrations`. Старая локальная база с таблицами, но без журнала, вызывает остановку с инструкцией резервного копирования; помощник не делает автоматическую отметку «применено» и не удаляет данные. Производственные миграции обслуживаются отдельно процессом публикации.

### Переход со старого каталога

Все прежние события с `is_demo=1`, а также пять известных стартовых идентификаторов считаются архивными. Они исключены из общего каталога и результатов, не принимают новые покупки и не могут быть возобновлены. Записи с историей показываются сотрудникам и владельцам связанных билетов; пять стартовых записей без реальных покупок скрыты полностью. Новые события сохраняются с `is_demo=0`.

Архивация не меняет исходный статус в БД, не удаляет историю и не начисляет возвраты автоматически. Интерфейс показывает незавершённый архив как приостановленный; завершённые и отменённые записи сохраняют соответствующий статус. Администрация отдельно рассматривает настоящие участия и при допустимом исходном статусе выполняет явную отмену. Завершённая историческая запись остаётся неизменяемой. Вымышленные пользователи/билеты не выводятся как настоящие участники.

## Целостность билетов и баланса

Вставка покупки запускает SQLite-триггеры: проверяются аккаунт, глобальное участие, архивность, время начала, баланс и остаток билетов. Та же транзакция выдаёт уникальные номера, списывает монеты, создаёт операцию, завершает заполненное событие и уведомляет участников. Повтор с тем же ключом покупки не списывает повторно. Параллельные последние билеты и отмена сериализуются SQLite.

Кандидат победившего номера генерируется на сервере Web Crypto с rejection sampling без смещения по модулю. Сохраняется только кандидат финальной покупки. Результат нельзя изменить через интерфейс. Публичный commit/reveal или независимый сервис доказательства случайности отсутствуют.

Одобрение запроса проверяет действующего администратора в SQL и начисляет монеты один раз. Ручная корректировка требует причины, не допускает отрицательный баланс и использует ключ повторного запроса на сотрудника. Операция, аудит и уведомление фиксируются атомарно. Покупки, перевода или вывода монет нет.

После первого билета фиксируются цена, вместимость, местоположение, начало, тип и наименование приза, а также изображение (`prizeType`, `prizeName`, `imageId`). Можно уточнять название и описание без изменения обещанных условий. В архиве набор не возобновляется, условия и приз фиксированы; незавершённую архивную запись можно отменить и уточнить её название и описание. Завершённые и отменённые события не редактируются. Отмена незавершённого события требует причины и один раз возвращает реальные списания, сохраняя билеты и историю. Стартовые билеты без покупки не создают возврат. Для новых/изменённых мест используется справочник; неизменённый старый текст местоположения допускается для совместимости.

Переключатели участия, запросов монет и создания обращений проверяются не только интерфейсом, но и при записи в БД. Существующие переписки можно продолжать при отключённом новом приёме. Ориентир ответа поддержки — информационная настройка, не планировщик автоматических ответов.

## Категории

Активные владелец, администратор и модератор создают категории действием `createCategory { name }`. Имя содержит 1–50 символов после NFKC, удаления крайних и свёртки повторных пробелов. Ключ сравнения не учитывает регистр и различие «е»/«ё»; повторное имя возвращает существующую каноническую категорию без повторного аудита. Можно сохранить до 100 новых категорий. Три начальные категории и категории прежних событий остаются доступными, неизменённый исторический текст сохраняется при редактировании. Общий список передаётся в `state.categories`.

## Призы и изображения

Создание события требует `prizeType` (произвольная непустая строка до 80 символов) и `prizeName` (до 120). `imageId` необязателен; без файла используется нейтральное оформление. Идентификатор выбранного изображения проверяется по D1.

`POST /api/prize-images` принимает multipart с единственным полем `file` от активного сотрудника. Ответ: `{ imageId, imageUrl, contentType, size }`, где `imageUrl` имеет вид `/api/prize-images/{id}`. Поддерживаются JPEG, PNG и WebP до 5 МиБ; проверяются размер реально прочитанного потока, сигнатура/заголовки контейнера, максимальная сторона 20 000 пикселей и площадь 40 мегапикселей. SVG и произвольные вложения не принимаются. Это проверка контейнера, не полноценное перекодирование изображения и не антивирусный сервис.

R2-привязка называется `BUCKET`. Объект сохраняется под внутренним ключом, метаданные — в `prize_images`. При неудачной записи метаданных сервис пытается удалить только что созданный объект. Получение файла требует входа на сайт и возвращает `nosniff` и приватное кеширование. Файлы предназначены для каталога, а не для приватных документов: вошедший посетитель может получить существующее изображение по его адресу.

Отдельной панели удаления объектов и автоматической уборки неиспользованных загрузок нет. При замене картинки или закрытии формы ранее загруженный объект может остаться в хранилище. Оператору нужно учитывать объём R2 и удалять ненужные объекты только после проверки ссылок из событий и резервной копии.

## Переписка, чтение и административные таблицы

Переписка двусторонняя: тема, статусы `open`/`in_progress`/`resolved`, приоритет, ответы, внутренние заметки и отметки прочтения. Сервер проверяет владельца обращения. Внутренние заметки не включаются в пользовательские ответы API и поиск. Обычный ответ возобновляет решённый вопрос. Отметка чтения принимает `readThrough` показанного снимка: более новый ответ остаётся непрочитанным. Лимит отправителя — 60 сообщений в час.

`/api/state` отдаёт ограниченный актуальный снимок для обновления интерфейса: до 200 переписок с последними 100 сообщениями, 1 000 пользователей/операций, 500 записей аудита и 10 000 строк билетов участников. Это не предел архива:

- `/api/support-threads` — серверный поиск, страницы списка и выбранное обращение;
- `/api/support-history` — предыдущие сообщения с курсором по времени и ID;
- `/api/admin-records` — страницы пользователей, запросов, операций, аудита и участников события, до 100 записей на запрос.

Административный поиск применяется до ограничения страницы. Экспорт проходит все подходящие страницы. Финансовые записи доступны только владельцу/администратору. Внутренние API не доверяют роли, присланной браузером. Личный пользовательский экран баланса использует недавний снимок; полный финансовый архив разбирает уполномоченная команда.

Административные изменения фиксируются в аудите. Баланс и отмена используют транзакционные триггеры; редактирование, права, настройки и действия поддержки сохраняют аудит вместе с изменением. Аудит решения по запросу условен и не пишет ложное успешное действие при конкурентном повторе. Тексты внутренних заметок в описание аудита не копируются.

## Telegram-кабинет

`/telegram` требует входа на сайт. `/api/telegram/link` выдаёт одноразовый код, принимает подтверждение и отключение владельца аккаунта. Код имеет срок 5 минут, в D1 сохраняется SHA-256-хеш. Приватный чат бота предъявляет код, затем пользователь отдельно подтверждает показанный числовой Telegram ID на сайте. Уникальные ограничения не позволяют одному действующему аккаунту иметь несколько привязок и одному Telegram ID принадлежать разным аккаунтам. Подтверждённая связь действует 30 дней; после окончания требуется повторное подтверждение через сайт.

Отдельный Node.js runner получает Telegram-updates через long polling. Закрытый `/api/telegram/bridge` принимает только `status`, `claimLink`, `state`, `prepareBuy`, `confirmBuy` и `requestCoins`. Платформенный сервисный доступ передаётся отдельно от `TELEGRAM_BRIDGE_SECRET`. Bridge проверяет свой секрет и не принимает от клиента роль или произвольный userId; пользователь определяется подтверждённой привязкой. Даже для сотрудника состояние собирается с пользовательскими правами, без административных таблиц и переписки поддержки. Сайт остаётся в существующей аудитории; публичный webhook для Telegram не добавляется.

Билеты используют те же покупки, триггеры, баланс и итог жеребьёвки. `prepareBuy` создаёт намерение на 5 минут, не резервируя билеты. `confirmBuy` проверяет текущую привязку, аккаунт, срок, количество и зафиксированную цену непосредственно при записи; ключ связан с намерением и исключает повторное списание. Идентификатор запроса монет также детерминирован для пользователя и повтора; повтор с отличающейся суммой/текстом не принимается как прежний. Отключение связи и блокировка запрещают новые действия, включая подтверждение прежнего неисполненного намерения.

Удаление приглашения Sites не отзывает сохранённую D1-привязку автоматически: при отзыве доступа нужно заблокировать аккаунт приложения либо отключить связь на сайте. Конечный 30-дневный срок не заменяет немедленный отзыв. Runner хранит на постоянном диске только offset обновлений, обрабатывает их последовательно и повторяет временные ошибки. Рестарт может повторить текстовый ответ; серверные ключи защищают изменения данных.

Инструкция по BotFather, секретам, запуску и восстановлению — [TELEGRAM_RU.md](docs/TELEGRAM_RU.md). Реальный токен, username и постоянный хост ещё не настроены, поэтому работа бота не подтверждена. Это чат-кабинет, не Mini App; просмотра уведомлений по команде достаточно для кабинета, но автоматическая рассылка и административные команды не заявляются.

## Проверки и эксплуатационные границы

`npm run check` запускает TypeScript и все серверные/SQL-тесты через `scripts/test-all.mjs`. Требуются Node.js ≥22.13 и Python 3. Тесты покрывают транзакции, конкурирующие покупки, повторные запросы, права, приватность сообщений, страницы истории, приглашения, архив и изображения. `npm run build` проверяет производственную сборку отдельно; успешная сборка не подтверждает визуальную проверку браузера.

GitHub Actions выполняет проверки, сборку и повторное применение локальных миграций к чистой временной базе. Доступ к производственным секретам и публикация ему не нужны.

Уведомления отображаются внутри сайта периодическим обновлением; отдельно подключённый Telegram-кабинет читает их по команде пользователя, без автоматической рассылки. Email, SMS, push, платежи, автоматическая передача призов, внешнее наблюдение за доступностью и независимый аудит случайности не подключены. Архив и CSV не заменяют резервное копирование D1/R2. Перед рабочим запуском нужны проверенная авторизация, реальные условия и призы, процесс поддержки/выдачи, мониторинг и проверка восстановления. Текущее состояние выпуска фиксируется отдельно в [RELEASE_READINESS_RU.md](docs/RELEASE_READINESS_RU.md).
